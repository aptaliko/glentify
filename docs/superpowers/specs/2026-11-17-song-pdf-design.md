# Song PDF (lyrics sheet) — design

Date: 2026-11-17 · Branch: `feat/song-pdf` (from `main`) · Repo: glentify (single repo)

## Intent and why

Some musicians keep their lyrics as a PDF rather than typed text. They should be able to
attach that PDF to a song and see it during a gig, in the live view, next to the song's
other content.

## Goals

- A song can have an optional lyrics PDF, stored separately from the score image.
- Admins and users can attach, replace and remove the PDF in the same three song editors
  that handle the image today (web new/edit, native offline edit).
- The live view shows every piece of content a song has, stacked top to bottom in the order
  **score image → lyrics PDF → typed lyrics**. A song with exactly one piece fills the view.
  A song with two or three pieces shows them one after another; the musician scrolls.
- The PDF is rendered in the app itself with pdf.js (canvas, page by page), so it behaves the
  same on web and on the Android app.
- Attaching a PDF works offline on native the same way the image does: the pick is stored
  locally, uploaded on reconnect, and the song row is written with the resulting URL.

## Non-goals (v1)

- Offline viewing of the PDF during a gig. The score image has no offline viewing today
  (the live view reads a remote URL), so the PDF matches that. See open question 1.
- Editing, annotating or highlighting the PDF.
- Extracting text from the PDF or searching it.
- Changing the program/sequence PDF export (`src/app/api/programs/[id]/pdf`, pdfkit), which
  is generation, not viewing.

## Anti-goals

- Hiding or breaking the existing image or typed-lyrics behaviour. A song with no PDF must
  look and behave exactly as it does now.
- Loading pdf.js or the PDF itself on pages that don't show the live view (lists, editors
  other than the file input).

## Constraints

- Vercel Blob client upload with an allowed-content-type list per route. The image route
  allows PNG/JPEG/WebP only; the PDF needs its own route or an allowed list that adds
  `application/pdf`.
- Server-side ceilings are duplicated in `src/lib/imageValidation.ts` and the upload route;
  the PDF ceiling must be mirrored the same way (client validation mirrors server limits).
- Native code calls the API only through `nativeApiFetch`; static export means no new
  server routes can be keyed by song id on device (the existing offline pattern handles it).
- Offline image flow is keyed by a negative draft blob id in `localImageStore` and
  resolved in `syncHandlers.ts` (`resolvePendingImageUrl`). The PDF reuses that shape.
- The `songs` table is the single song row; `SongRow` already flows into the offline
  reference-data blob, so a new column reaches the device without new plumbing beyond the
  cached-song type.

## Approaches considered

1. **Browser built-in PDF embed** (`<object>`/`<iframe>`). No dependency. Rejected: the
   Android web view often cannot show PDFs inline, which is the device used at gigs.
2. **pdf.js, page by page on canvas** — *chosen (B)*. Same rendering on web and Android,
   fits the scrolling stack, works with the existing pinch-zoom wrapper. Cost: a sizeable
   library and a worker file bundled into the app.
3. **Open the PDF in another app.** Rejected: leaves the live view, breaks the stacked scroll.

## Design

### Data model
- New nullable column `songs.pdf_url text` (migration generated by `npm run db:generate`).
  Not an axis; nothing in `songAxisValues` changes.
- `SongRow` gains `pdfUrl`. `CachedSong` (src/lib/referenceData.ts) gains `pdfUrl: string | null`
  so the offline blob type matches the server row. Normalization backfills `pdfUrl ?? null`
  for blobs primed before this change.

### Upload
- New route `src/app/api/songs/pdf-upload/route.ts`, same shape as the image route:
  `allowedContentTypes: ['application/pdf']`, `maximumSizeInBytes` = 10 MB,
  `addRandomSuffix: true`, behind the same proxy auth.
- `src/lib/pdfValidation.ts`: `ALLOWED_PDF_TYPE`, `MAX_PDF_BYTES` (10 MB), `validatePdfFile`,
  mirroring `imageValidation.ts`, with Greek inline error text.

### Editors (web and native)
- Each of the three song editors (`admin/songs/new`, `admin/songs/[id]`,
  `admin/local/songs/edit`) gets a second file input "Στίχοι σε PDF" beside the image input,
  with a preview link and a "Αφαίρεση PDF" action (mirrors the image remove action).
- The payload carries `pdfUrl` on web, and `pendingPdfBlobId` + `pdfUrl` offline.

### API
- `POST /api/songs` and `PATCH /api/songs/[id]` accept `pdfUrl: string | null`, validated
  as `z.string().nullable()` exactly like `imageUrl` (my call: match the existing field).

### Offline (native)
- `CreateSongPayload` / `UpdateSongPayload` gain `pendingPdfBlobId` and the store
  `localImageStore` keeps PDF bytes under the same draft-id scheme (separate key namespace
  to avoid colliding with image draft ids, e.g. a `kind` field).
- `syncHandlers.ts`: `resolvePendingPdfUrl` mirrors `resolvePendingImageUrl` (same
  `item-error` / `systemic-error` mapping, same already-uploaded map).
- `songsMerge.ts` overlays a pending PDF the same way it overlays a pending image.

### Live view (display)
- `LiveSessionView` receives `pdfUrl` next to `imageUrl`, and `lyrics`.
- A pure function `selectStackBlocks({ imageUrl, pdfUrl, lyrics })` returns the ordered list of
  blocks present (`'image' | 'pdf' | 'lyrics'`). It is unit-tested. The view renders those
  blocks in order inside one vertically scrollable container.
- Single block: fills the view as today (image keeps its existing pinch-zoom wrapper; the
  lyrics block keeps its font-size and stage-mode controls).
- Two or three blocks: each block gets its natural height; the container scrolls.
- PDF block: pdf.js loads the URL, renders every page full-width to a canvas, pages stacked
  vertically. The pdf.js worker is served from the app's static files (copied at build).
  Loading state and a Greek error message if the PDF fails to load.
- Stage mode and the lyrics font controls keep working inside the lyrics block.

### Sessions / sequence pages
- `sessionStore.ts` and the three pages that render `LiveSessionView` pass `pdfUrl` through
  from the song row (`programs/[id]/sequences/[seqId]`, `session/[id]`, `session/local`,
  `programs/local/sequence`).

### Testing
- Unit (Vitest, pure logic only, per repo convention): `selectStackBlocks` (every combination
  of present/absent and the order), `validatePdfFile` (type, size), `normalizeReferenceData`
  pdfUrl backfill, offline PDF overlay in `songsMerge`.
- Manual (docs/manual-testing-checklist.md): attach/replace/remove PDF on web; on native
  offline attach → reconnect → URL on the song; live view shows the blocks in order for each
  combination; scrolling with two blocks; PDF rendering on the Android device.

## Left to the builder (my calls, not yet agreed)

- PDF size ceiling: 10 MB, same as the image.
- Only the first 50 pages are rendered, to bound memory on the phone (lyrics sheets are short).
- pdf.js version: the newest stable release at implementation time, pinned exactly.
- The PDF block scrolls with the page, not inside its own scroller.

## Open questions (theirs)

1. **Offline during a gig.** Should lyrics PDFs be cached on the device so they show without
   a connection? Today the score image does not work offline either. My default: no for v1,
   matching the image. Caching means downloading the PDFs during the offline prime and
   storing bytes locally, which is a separate, larger piece of work.
2. **Interpretation check.** I'm reading "more than 2" as "when more than one piece is
   available", so 2 or 3 stacked, and 1 fills the view. Correct?
